## 2024-05-14 - Map arrays to Set in deep loops
**Learning:** The application heavily iterates over `state.routines` and `state.completions` during UI rendering loops. When evaluating active states inside these deep loops, always mapping arrays into O(1) `Set` objects beforehand prevents UI thread blocking from repeating O(N) array methods.
**Action:** Always create `Set` objects for lookups in tight loops, particularly for `id` filtering.
## 2024-09-04 - Precomputing routine masks and HTML strings in calendar loops
**Learning:** In deep UI rendering loops for the annual heatmap/calendar (like `renderYearGrid`), parsing sets and running `.includes()` repeatedly for routines causes a massive performance bottleneck. Also, generating individual `<span class="...">` sub-boxes with template literals creates enormous memory overhead and GC pressure. Pre-calculating bitmasks for the days each routine is active, combined with pre-assembling the HTML strings for each possible state (future, completed, missed, inactive) outside the loop provides ~15-20% execution speed up for rendering 365 days of sub-boxes.
**Action:** Extract routine `.includes()` into pre-computed bitmasks, and extract repeated HTML strings into pre-compiled string arrays before iterating over date ranges to minimize garbage collection and string parsing.
## 2024-09-04 - DST timezone regression in date loops
**Learning:** In date loops across months, never replace `new Date(Y, M, D)` with a `timestamp += 86400000` counter. Daylight Saving Time (DST) makes some days 23 or 25 hours long. Adding exactly 24 hours across a DST boundary shifts the timestamp to 01:00 AM or 23:00 PM, destroying midnight alignment and causing `timestamp > todayMidnight` comparisons to falsely trigger.
**Action:** When avoiding `new Date()` allocation in loops for date comparisons, use lexicographical string comparison of ISO-formatted strings (e.g., `dateStr > todayStr`) instead, as `YYYY-MM-DD` perfectly aligns with chronological order and ignores timezone shifts.
## 2024-09-04 - UTC offsets in toISOString
**Learning:** Using `toISOString().split('T')[0]` generates a UTC date string, not a local one. In timezones behind UTC (like EST/UTC-5), this string rolls over to the "next" day at 7 PM or 8 PM local time. If used for calendar comparisons (like checking if a cell is "in the future"), it introduces severe timezone bugs where the app treats tomorrow as today in the evening hours.
**Action:** Always manually construct local date strings using `getFullYear()`, `getMonth()`, and `getDate()` when replacing local `Date` object comparisons with string comparisons.
